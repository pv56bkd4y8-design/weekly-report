# 写周报

## 核心原则

1. **忠于事实**：用户没说过的具体事实（数据、方法、策略）不得编造。管控举措如用户未提及，应追问或根据用户描述合理推导（推导须标注为推导并请用户确认），不得直接当作事实输出。
2. **信息密度优先**：每句话必须传递有效信息。删掉一切"积极推进""有序开展""持续跟进"等无信息量的套话。
3. **结构化思维**：按重要性排序，重点项目详写、次要项目略写，不是流水账。
4. **可验证性**：成果必须可量化或有明确的完成状态标记，让读者能判断进展。
5. **跨周闭环**：上周计划必须在「本周工作完成情况」中逐条兑现，形成"计划→执行→复盘"的闭环。未兑现项须说明原因和后续安排，不允许无声消失。不设独立的「上周计划回顾」板块。

## 内容风格

- 正式商务风格，条理清晰
- 每个项目三要素：**做了什么 + 做到什么程度 + 怎么保证做好**
- 使用专业术语，避免口语化
- 关键数据和成果必须量化（如"完成 212 题""覆盖 3 个模块"）
- 无法量化时，用完成状态标记（已上线 / 已完成评审 / 进行中 80% / 已延期）

## 工作流

### 步骤 1：识别输入类型并收集信息

用户输入通常有三种形式，按形式采取不同策略：

**流水账式**（"这周做了 A 还有 B 然后 C..."）
→ 提取所有项目，按重要性重新排序，追问缺失的量化数据

**结构化列表式**（已按项目分条列出）
→ 逐条检查三要素是否完整，追问缺失项

**概括式**（"这周主要在做登录重构"）
→ 逐项追问：具体做了什么？完成了多少？质量怎么保证的？

**必须收集的信息：**

| 板块 | 必填 | 收集内容 |
|------|------|---------|
| 本周工作 | 是 | 项目名称、达成结果、关键管控举措 |
| 下周计划 | 是 | 项目名称、验收标准、管控举措 |
| 问题与卡点 | 否 | 问题描述、影响范围、建议方案 |
| 总结与反思 | 否 | 优点（须具体）、优化思考（须可执行） |

**追问策略：**
- 一次性列出所有缺失项，不要逐个追问
- 优先追问量化数据（"完成了多少？""涉及几个模块？"）
- 管控举措如果用户没提，先根据工作内容推导一个版本，明确告知用户"以下是我根据内容推导的管控举措，请确认或修改"

**跨周连续性处理：**
- 如果用户提供了上周计划（或要求对比上周），主动询问上周各项目的完成情况
- 对比维度：是否按期完成、实际成果 vs 预期目标、未完成原因
- 对于上周计划中本周未完成的项目，需追问：是延期、取消、还是调整到其他时间？
- **写入位置**：不设独立回顾板块，也不设「上周计划兑现」字段；上周计划的进展、延期原因、完成度自然写入「达成结果」
- **合并规则**：上周计划项与本周同一项目只写一条，不重复罗列

### 步骤 2：整理与排序

**排序规则：** 按以下优先级排列项目：
1. 有明确交付物/上线的项目（最优先）
2. 本周推进最多的项目
3. 跨团队协作项目
4. 日常维护性工作（放最后，合并简写）

**详略规则：**
- 重点项目（前 2-3 个）：完整写三要素，每条 2-3 行
- 次要项目：可合并为一条，简述成果即可
- 日常事务（如修 bug、参加会议）：合并为一条，只写量化结果

**分项目分块规则：**
- 「本周工作完成情况」和「下周工作计划」须按项目/产品线分块，块标题用【项目名】格式
- 常见分块：【AI素养项目】【CATA项目】【关岗项目】【客户共建】等，按用户实际工作灵活命名
- 同一板块内条目连续编号（1. 2. 3. ...），换块不重置编号
- 每块内按重要性排序；整块无内容则省略该块标题

### 步骤 3：润色与转换

**口语→书面转换参考表：**

| 用户原话 | 周报表述 |
|---------|---------|
| 修了 N 个 bug | 修复 N 个线上缺陷 |
| 跟 XX 对了需求 | 与 XX 完成需求对齐 |
| 做完了 / 搞定了 | 已完成开发并通过测试 |
| 还在做 | 进行中，当前完成约 X% |
| 上线了 | 已全量发布上线 |
| 写了个方案 | 输出 XX 方案文档 |
| 开了个会 | 组织/参与 XX 评审会，达成 XX 结论 |
| 帮忙看了 XX | 完成 XX 评审/审查 |
| 调研了一下 | 完成 XX 技术调研，结论为... |

**管控举措写作原则：**
- 必须具体可执行，禁止空泛表述
- 好：分阶段灰度发布，每阶段观察 24 小时无异常后推进下一阶段
- 好：修复后完成回归测试及线上验证，覆盖核心链路用例
- 差：确保质量（空话）
- 差：积极推进（无信息量）
- 差：持续跟进（没说跟什么、怎么跟）

**如果无法为用户的项目写出具体管控举措，说明信息不足，应追问而非编造。**

### 步骤 4：输出周报

```
一、本周工作完成情况

【AI素养项目】

1. 项目名称
   达成结果：具体做了什么 + 做到什么程度 + 量化成果（完成度、延期原因等写在达成结果中，不单列进度状态）
   关键管控举措：怎么保证做好的

2. 项目名称
   ...

【CATA项目】

3. 项目名称
   ...

二、现存问题与卡点

1. 问题描述
   影响：对进度/质量/资源的具体影响
   建议：建议的解决方案或需要的支持

三、本周总结与优化反思

1. 优点：（须基于本周具体事实，不写空泛表扬）
2. 优化思考：（须为可落地的改进动作，不写"继续加强""进一步提升"等套话）

四、下周工作计划

【AI素养项目】

   达成程度（验收标准）：可衡量的交付目标
   关键管控举措：怎么保证做好的

   ...
```

## 输出规则

- 语言：中文
- 格式：纯文本，不用 Markdown 标记（不用 `#`、`**`、`-`）
- 编号：大板块用中文数字（一、二、三、四），子项用阿拉伯数字（1. 2. 3.），跨项目块连续编号
- 分块：本周工作和下周计划须用【项目名】分块，块标题独占一行
- 项目名称独占一行以突出显示
- 没有内容的可选板块整块省略
- 不加日期标题（用户自行添加）
- 总长度控制：本周工作每个项目 2-4 行，全篇周报不超过两屏

## 反模式清单（禁止出现）

- 空话套话：积极推进、有序开展、持续跟进、大力推动、全面落实
- 虚假量化：完成了"若干"任务、取得了"良好"效果（"若干""良好"不是量化）
- 编造事实：用户没提的方法、策略、数据不得作为事实输出
- 无信息量总结："本周工作整体顺利"（没说具体哪里顺利）
- 套话反思："需要进一步加强沟通协作"（没说怎么加强、跟谁、在哪方面）
- 过度美化：把普通工作描述得像是重大突破
- 流水账：不做排序和归类，按用户原话顺序罗列
- 遗忘承诺：上周计划的项目本周未提及，既不说明完成情况也不解释原因
- 虚假完成：上周计划"完成开发"，本周写"已完成"但实际只完成了 60%
- 回避延期：上周计划本周未完成，但不说明原因和调整方案

## 修改迭代

用户要求修改时：
- 调整语气（更正式/更简洁）：直接改
- 补充信息：替换对应条目，保持整体结构
- 删减内容：删除后重新检查排序和详略是否合理
- 每次修改后输出完整周报，不输出片段

## 完整示例

### 示例 1：无上周计划对比

**用户输入：**
> 这周做了用户中心的登录重构，把原来的短信验证码换成了支持邮箱+短信两种方式，已经上线了。还修了几个线上 bug，大概 3 个。跟产品对了下个版本的需求。下周要继续做注册流程的重构。有个问题是第三方支付接口文档太老了，需要找对方确认。

**agent 追问：**
> 收到，补充几个信息我就能帮你写：
> 1. 登录重构的管控举措是什么？（比如灰度发布、A/B 测试、还是直接全量？）
> 2. 3 个 bug 大概涉及哪些模块？
> 3. 需求对齐的结果是什么？明确了几项功能？
> 4. 下周注册流程重构预计完成到什么程度？

**用户补充：**
> 登录重构是灰度上的，先 10% 用户观察了一天没问题再全量。bug 是登录超时、验证码收不到、页面白屏。需求对了 5 个功能点。注册流程下周争取做完开发。

**输出：**

```
一、本周工作完成情况

1. 用户中心登录模块重构
   达成结果：完成登录模块架构重构，新增邮箱+短信双通道验证能力，已全量上线
   关键管控举措：采用灰度发布策略，首批 10% 用户灰度观察 24 小时无异常后全量切换

2. 线上缺陷修复
   达成结果：修复 3 个线上缺陷（登录超时、验证码接收失败、页面白屏），均涉及核心链路
   关键管控举措：修复后完成回归测试及线上验证，确认无二次影响

3. 下版本需求对齐
   达成结果：与产品完成需求方案评审，明确 5 项核心功能点及优先级排序
   关键管控举措：输出需求评审纪要，各方确认后进入开发排期

二、现存问题与卡点

1. 第三方支付接口文档版本过旧，部分字段定义与现行接口不一致
   影响：可能导致对接联调周期延长
   建议：尽快联系支付方技术对接人确认最新接口规范

三、本周总结与优化反思

1. 优点：登录重构通过灰度策略平稳上线，线上缺陷当日修复闭环
2. 优化思考：外部依赖对接应在项目启动阶段即确认接口文档版本，避免联调阶段才发现不一致

四、下周工作计划

1. 用户中心注册流程重构
   达成程度（验收标准）：完成注册流程核心逻辑开发，通过功能测试
   关键管控举措：按模块拆分开发任务，注册与登录共用组件优先开发并复用验证
```

### 示例 2：有上周计划对比

**用户输入：**
> 上周计划：1. 完成登录重构开发 2. 输出支付模块技术方案 3. 修复 5 个线上 bug。这周登录重构已经上线了，支付方案只写了一半，bug 修了 3 个。另外临时加了个紧急需求，帮运营导数据。下周继续做注册重构。

**agent 追问：**
> 收到，对比上周计划补充几个信息：
> 1. 支付方案为什么只完成一半？是遇到技术问题还是被其他事情打断？预计什么时候完成？
> 2. 上周计划修 5 个 bug，实际修了 3 个，剩下 2 个是延期到本周还是取消了？
> 3. 登录重构的管控举措是什么？（灰度还是直接全量？）
> 4. 运营导数据的工作量大概多少？涉及多少数据量？

**用户补充：**
> 支付方案是因为等财务确认业务规则耽误了 2 天，下周一下午能完成。剩下 2 个 bug 优先级低，推到下周了。登录是灰度上的，10% 用户观察一天。运营导了 3 万条用户数据。

**输出：**

```
一、本周工作完成情况

1. 用户中心登录模块重构
   达成结果：完成登录模块架构重构，新增邮箱+短信双通道验证能力，已全量上线
   关键管控举措：采用灰度发布策略，首批 10% 用户灰度观察 24 小时无异常后全量切换

2. 支付模块技术方案
   达成结果：完成方案主体框架撰写（50%），等待财务确认业务规则耽误 2 天，业务规则细节待确认后定稿，预计下周一完成
   关键管控举措：周一上午与财务完成最终确认，下午组织技术评审会

3. 线上缺陷修复
   达成结果：本周修复 3 个线上缺陷（登录超时、验证码接收失败、页面白屏），累计完成 60%；剩余 2 个低优先级 bug 调整至下周
   关键管控举措：修复后完成回归测试及线上验证

4. 运营数据导出支持
   达成结果：完成运营部门紧急数据需求，导出 3 万条用户数据并完成数据校验
   关键管控举措：数据导出前完成脱敏处理，导出后与运营确认数据完整性

二、现存问题与卡点

1. 支付模块技术方案依赖财务业务规则确认
   影响：方案输出延期 2 天，可能影响后续开发排期
   建议：建立跨部门需求确认的 SLA 机制，明确响应时效

三、本周总结与优化反思

1. 优点：登录重构通过灰度策略平稳上线，紧急需求响应及时
2. 优化思考：跨部门依赖项应提前 3-5 个工作日启动确认流程，避免成为关键路径瓶颈

四、下周工作计划

1. 用户中心注册流程重构
   达成程度（验收标准）：完成注册流程核心逻辑开发，通过功能测试
   关键管控举措：按模块拆分开发任务，注册与登录共用组件优先开发并复用验证

2. 支付模块技术方案
   达成程度（验收标准）：周一下午前完成完整方案并通过技术评审
   关键管控举措：周一上午与财务完成最终确认，下午组织技术评审会

3. 线上缺陷修复
   达成程度（验收标准）：完成剩余 2 个低优先级 bug 修复
   关键管控举措：修复后完成回归测试及线上验证
```
